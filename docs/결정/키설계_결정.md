# 키 설계 결정 기록

## 1. 배경

### 무엇을 저장하는가
TFDS-Edu 터널 센서의 원본 로그. 한 덩어리는 센서 하나의 한 시간치이다.

### 누가 읽는가
5주차 이후 원본 로그를 날짜별로 조회하고 처리하는 데이터 파이프라인

---

## 2. 검토한 후보

| 후보 | 쉬워지는 것 | 어려워지는 것 |
|---|---|---|
| 센서/날짜/시각 | 센서 하나의 장기 이력 조회 | 하루치 전체 조회 시 센서별로 순회해야 함 |
| 날짜/센서/시각 | 특정 날짜 전체 조회, 날짜 단위 정리 | 센서 하나의 장기 이력이 여러 날짜 prefix로 흩어짐 |
| 날짜/시각/센서 | 특정 시간 구간 조회 | 센서 기준 조회가 가장 비쌈 |

---

## 3. 결정

### 선택한 키 구조

**날짜/센서/시각**

### 예시

2026-09-14/sensor-01/09.txt
2026-09-14/sensor-01/10.txt
2026-09-14/sensor-02/09.txt

### 결정 이유

원본 로그를 날짜 단위로 조회하고 정리하는 작업을 쉽게 하기 위해 날짜를 가장 앞에 둔다.

특정 날짜의 여러 센서 데이터를 하나의 접두어 아래에서 조회할 수 있고 날짜 단위 삭제도 쉽다.

---

## 4. 무엇을 포기했는가 ★

센서를 앞에 뒀다면 센서 하나의 장기 이력을 하나의 접두어로 쉽게 조회할 수 있었다.

날짜를 앞에 두면서 센서별 장기 이력이 날짜별로 흩어지는 것을 포기했고, 대신 날짜 단위 조회와 정리를 쉽게 했다.

날짜/시각/센서를 선택했다면 시간 구간 조회가 더 쉬웠겠지만 센서 기준 조회 비용이 커지는 것을 피했다.

### 다시 검토할 조건

읽는 쪽이 날짜별 조회보다 특정 센서의 장기 이력을 주로 조회하기 시작하면 이 결정을 다시 검토한다.

---

## 5. 영향

### 조회

날짜 prefix로 특정 날짜의 전체 센서 로그를 쉽게 조회할 수 있다.

### 정리

날짜 prefix를 기준으로 오래된 날짜의 데이터를 묶어서 정리하기 쉽다.

### 다음 주 이후

5주차부터 들어오는 실제 원본 로그도 날짜/센서/시각 순서의 key 규약을 따른다.
