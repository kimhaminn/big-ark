# 4주차 실습 안내 — 브로커 한 칸을 연다

> **빅데이터 엔지니어링 · 4주차 실습 (90분)**
> 투사 화면에는 작업 순서만 나온다. **명령과 확인 방법은 이 문서를 본다.**

> **3주차 산출물(객체 저장소)이 살아 있어야 P0 이 짧게 끝난다.** 안 되어 있으면 P0 에서 닫고 간다.

> ★ **오늘 새로 설치하는 것은 없다.** 브로커 이미지 하나를 받고, **나머지는 전부 그 컨테이너 안에 이미 들어 있는 명령**으로 한다.

---

## 0. 오늘 하는 것

| 과제 | 무엇을 하는가 | 완료 판정 |
|---|---|---|
| **P0** | 지난주 것 확인 | 구성 파일을 열어 놓고 P1 을 시작할 수 있다 |
| **P1** | 브로커를 올린다 — 컨테이너 하나 | **호스트에서** 토픽 목록이 나온다 |
| **P2** | **토픽을 설계한다** | 토픽 3개 이하이고 세 근거를 말로 댈 수 있다 |
| **P3** | 소비자 셋을 붙인다 | 하나를 멈춰도 나머지 둘이 가고, 재기동 시 이어진다 |
| **P4** | 빼기 회고 | **「뺀다 ↔ 잃는 것」**이 짝으로 적혀 있다 |

**오늘 남기는 것 넷** — 서비스가 하나 더 늘어난 구성 파일 · **토픽 설계서 1장** · 소비자 3계통이 붙은 상태 · 회고 답안 1장

★ **오늘 채점하는 것은 「떴는가」가 아니다.** 뜨는 것은 이 문서를 따라 하면 된다. 채점하는 것은 **왜 그렇게 갈랐는가**다.

> **P2 에는 칠 명령이 거의 없다.** 30분 동안 만드는 것은 실행 결과가 아니라 **문서 한 장**이다. 손이 논다고 느껴도 그것이 정상이다.

## 브로커 이미지

**`apache/kafka:4.3.1`** 을 쓴다. **각자 받는다.**

```bash
docker pull apache/kafka:4.3.1
```

받는 동안 P0 을 진행한다. **먼저 이 명령을 걸어 두고 아래로 내려간다.**

---

## 오늘 쓰는 명령의 모양

**Kafka 명령은 전부 컨테이너 안에 있다.** 그래서 모양이 늘 같다.

```bash
docker compose exec broker /opt/kafka/bin/<명령>.sh --bootstrap-server localhost:9092 …
```

길다. **터미널마다 한 번씩 별칭을 만들어 두면 이후가 짧아진다.**

```bash
# 리눅스 · macOS · WSL · Git Bash
alias kf='docker compose exec broker /opt/kafka/bin'

# PowerShell
function kf { docker compose exec broker /opt/kafka/bin/$args }
```

아래 문서는 **긴 형태로 적는다.** 별칭을 만들었으면 `docker compose exec broker /opt/kafka/bin` 자리를 `kf` 로 바꿔 읽는다.

## P0 · 지난주 것이 살아 있는지 확인 (5분)

**① 지난주 컨테이너가 떠 있는가**

```bash
docker compose ps
```

객체 저장소가 `running` 이면 통과다. 없으면 지난주 폴더에서 올린다.

```bash
docker compose up -d
```

**② 지난주 구성 파일을 연다**

P1 이 **이 파일에 서비스를 더한다.** 새 파일을 만들지 않는다.

**③ 9092 가 비어 있는지 본다**

브로커가 호스트에 여는 포트는 **9092 하나**다.

```bash
# 리눅스 · macOS · WSL
ss -lntp | grep 9092     # 또는  lsof -i :9092

# PowerShell
Get-NetTCPConnection -LocalPort 9092 -ErrorAction SilentlyContinue
```

아무것도 안 나오면 통과다. 나오면 손을 든다.

**④ 결정 기록 자리가 있는가**

2주차에 만든 문서 구조 안에 결정 기록을 넣는 자리가 있어야 한다. **P2 의 설계서가 여기 붙는다.**

> **지난주 미완인 사람은 지금 말한다.** 여기서 닫고 간다. 넘기면 P1 에서 두 배로 든다.

## P1 · 브로커를 올린다 (25분)

**① 구성 파일에 브로커 서비스 블록을 추가한다**

아래를 지난주 구성 파일의 `services:` 아래에 붙여 넣는다.

```yaml
  broker:
    image: apache/kafka:4.3.1
    container_name: tfds-broker
    ports:
      - "9092:9092"                       # 호스트에서 붙는 포트. 이 하나면 된다
    environment:
      # ── 이 노드가 맡는 역할 두 가지 ──────────────────────────
      KAFKA_PROCESS_ROLES: "broker,controller"
      KAFKA_NODE_ID: "1"
      # 컨트롤러가 하나뿐이므로 자기 자신이 쿼럼이다
      KAFKA_CONTROLLER_QUORUM_VOTERS: "1@localhost:9093"
      # ── 어디서 듣고, 밖에 무엇이라고 알려줄 것인가 ───────────
      KAFKA_LISTENERS: "PLAINTEXT://:9092,CONTROLLER://:9093"
      KAFKA_ADVERTISED_LISTENERS: "PLAINTEXT://localhost:9092"
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: "PLAINTEXT:PLAINTEXT,CONTROLLER:PLAINTEXT"
      KAFKA_CONTROLLER_LISTENER_NAMES: "CONTROLLER"
      # ── 노드가 하나라 복제본을 둘 곳이 없다 ─────────────────
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: "1"
      KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR: "1"
      KAFKA_TRANSACTION_STATE_LOG_MIN_ISR: "1"
    volumes:
      - broker-data:/var/lib/kafka/data

# 파일 맨 아래 volumes: 절에 한 줄 더한다
#   broker-data:
```

**② ★ 블록을 읽는다 — 없는 것과, 밖으로 안 나가는 것**

- **별도 합의 계층 서비스가 없다.** 3교시에서 본 오른쪽 그림이 이것이다. 예전에는 여기에 컨테이너가 하나 더 있었다
- **포트를 하나만 열었다.** `9093` 은 `KAFKA_LISTENERS` 에는 있는데 `ports:` 에는 없다 — **컨트롤러는 자기 자신하고만 말하므로 밖으로 낼 이유가 없다**

**③ 올린다**

```bash
docker compose up -d broker
docker compose logs -f broker      # Ctrl+C 로 빠져나온다
```

로그가 흐르다 멈추고 기동 완료 줄이 보이면 된다.

> ★ **이 이미지는 저장소 포맷을 자동으로 한다.** 로그에 「포맷되지 않았다」는 줄이 나오면 아래를 친다.
> ```bash
> docker compose exec broker /opt/kafka/bin/kafka-storage.sh random-uuid
> docker compose exec broker /opt/kafka/bin/kafka-storage.sh format \
>   -t <위에서 나온 UUID> -c /opt/kafka/config/server.properties
> ```

**④ 호스트에서 토픽 목록을 조회한다**

```bash
docker compose exec broker /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --list
```

**완료** — 아무것도 안 나와도 통과다. **빈 목록이 나오는 것**이 브로커가 답했다는 뜻이다.

### 판단 — 답할 수 있어야 한다

> **복제 계수를 1 로 둘 수밖에 없는 이유는 무엇인가. 그래서 무엇을 포기했는가.**

### 막혔을 때 — 순서대로 본다

| 증상 | 먼저 볼 것 |
|---|---|
| 컨테이너가 떴다가 바로 죽는다 | `docker compose logs broker` — 대개 **환경변수 오타** |
| 목록 조회가 응답 없이 멈춘다 | `KAFKA_ADVERTISED_LISTENERS` — 여기가 틀리면 브로커는 살아 있는데 안 붙는다 |
| 포트가 이미 쓰인다 | P0 ③ 으로 돌아간다 |
| `NODE_ID` 관련 오류 | 볼륨에 옛 포맷이 남았다. 아래로 처음부터 |

```bash
# 처음부터 다시 (볼륨까지 지운다)
docker compose down -v
```

## P2 · 토픽을 설계한다 (30분) ★오늘의 중심

**칠 명령은 ⑥ 한 줄뿐이다.** 나머지 25분은 근거를 만드는 데 쓴다.

### ① 무엇을 가를 것인가

TFDS-Edu 는 터널 센서 데이터를 받는다. 가르는 방법이 둘이다.

| 안 | 토픽 | 무엇이 걸리는가 |
|---|---|---|
| 센서 종류별 | `temp` · `smoke` · `co` · … | 센서가 20종이면 토픽이 20개가 된다 |
| 데이터 성격별 | `sensor-raw` · `sensor-verdict` | 소비자가 종류를 골라 읽을 수 없다 |

> **센서가 20종이라고 토픽을 20개 만들지 않는 이유**를 설계서에 적는다. 소비자 쪽에서 무슨 일이 생기는지를 생각한다.

### ② 파티션 수를 정한다 ★되돌릴 수 없다

**늘릴 수는 있으나 줄일 수 없다.** 그리고 바꾸는 순간 **키의 배정이 바뀐다** — 같은 센서의 데이터가 어제와 오늘 다른 파티션에 들어가고, 그 경계에서 순서 보장이 끊긴다.

그렇다고 넉넉히 잡는 것도 공짜가 아니다. 파티션이 늘면 **파일 핸들과 리밸런싱 비용**이 함께 는다.

> 몇으로 정했든 **그 여유의 대가**를 설계서에 한 줄 적는다.

### ③ 키를 정한다

센서 ID 를 키로 두면 —

- **보장되는 것** — 같은 센서의 메시지는 같은 파티션으로 가므로 그 안에서 순서가 사실이다
- **보장되지 않는 것** — 서로 다른 센서 사이에는 순서가 없다

> **대부분의 경우 이것으로 충분하다.** 전역 순서가 정말 필요한지 먼저 묻는다 — 필요하다고 잘못 판단하면 파티션 1개로 가고 병렬을 통째로 잃는다.

★ **P3 에서 이 키를 손으로 쳐 넣는다.** 어느 파티션에 떨어지는지 눈으로 본다.

### ④ 보존 기간을 정한다

소비와 무관하게 남는다. **그 값이 곧 디스크다.**

```
하루 메시지 수 × 메시지 크기 × 보존 일수 = 대략의 디스크
```

### ⑤ ★ 설계서 한 장을 쓴다

`토픽설계서_양식.md` 를 복사해 채운다. **근거란이 비면 미통과다.**

### ⑥ 그 설계대로 토픽을 만든다

```bash
docker compose exec broker /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --create \
  --topic <설계한 이름> \
  --partitions <설계한 수> \
  --replication-factor 1 \
  --config retention.ms=<설계한 보존 기간(밀리초)>
```

확인한다.

```bash
docker compose exec broker /opt/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 --describe --topic <이름>
```

**완료** — 토픽 **3개 이하**이고, ①②③ 의 근거를 **말로** 댈 수 있다.

## P3 · 소비자 셋을 붙인다 (20분)

**터미널을 넷 연다.** 셋은 소비자, 하나는 생산자다.

**① 소비자 셋을 그룹만 바꿔 띄운다**

터미널 1·2·3 에서 각각 —

```bash
# 터미널 1 — 처리 계통 흉내
docker compose exec broker /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic <토픽> \
  --group proc --from-beginning \
  --property print.key=true --property print.partition=true

# 터미널 2 — 시계열 적재 계통 흉내   → --group store
# 터미널 3 — 아카이브 계통 흉내      → --group archive
```

`--group` 만 다르고 나머지는 같다. **셋은 서로를 모른다.**

**② 터미널 4 에서 메시지를 넣는다**

```bash
docker compose exec broker /opt/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic <토픽> \
  --property parse.key=true --property key.separator=:
```

프롬프트가 나오면 **`키:값` 형태로** 한 줄씩 친다. 키는 P2 ③ 에서 정한 것이다.

```
센서-01:{"temp":21.5}
센서-02:{"temp":22.1}
센서-01:{"temp":21.7}
센서-03:{"temp":30.4}
```

★ **소비자 화면에 `Partition:N` 이 함께 찍힌다.** **같은 키는 늘 같은 파티션**으로 간다 — `센서-01` 두 줄이 같은 번호에 떨어지는지 본다. P2 ③ 에서 글로 적은 것이 여기서 눈으로 확인된다.

**③ 셋이 같은 메시지를 각자 받는지 본다**

터미널 1·2·3 **전부**에 같은 줄이 찍힌다. **나눠 갖는 게 아니라 각자 다 받는다.**

**④ ★ 하나를 멈춘다**

터미널 3(`archive`)에서 `Ctrl+C`. 터미널 4 에서 몇 줄 더 넣는다.

**나머지 둘은 그대로 받는다.** 영향받지 않는 것이 정답이다.

**⑤ 멈춘 것을 다시 붙인다**

터미널 3 에서 ① 의 `archive` 명령을 그대로 다시 친다.

> **`--from-beginning` 이 있는데도 처음부터 읽지 않는다.** 그 옵션은 **그룹에 저장된 위치가 없을 때만** 쓰인다. 이미 어디까지 읽었는지 기억하고 있으므로 **멈춘 데서 이어진다.**

**⑥ 그룹 ID 를 빼고 하나 띄워 본다**

```bash
docker compose exec broker /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic <토픽> --from-beginning
```

띄울 때마다 **처음부터** 읽힌다. `--group` 을 안 주면 매번 새 그룹이 만들어지기 때문이다 — **기억할 위치가 없으니 처음부터다.**

**⑦ 같은 그룹에 하나 더 붙인다 — 무엇이 멈추는지 본다**

터미널 5 를 열고 **프로토콜을 지정해서** `proc` 그룹에 붙인다.

```bash
# 예전 방식 — 그룹 전원이 손을 뗐다가 다시 모인다
docker compose exec broker /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic <토픽> --group proc \
  --consumer-property group.protocol=classic
```

**먼저 붙어 있던 터미널 1 까지 함께 잠깐 멈춘다.** 그것이 리밸런싱이다.

이번엔 새 방식으로 같은 것을 해 본다.

```bash
docker compose exec broker /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic <토픽> --group proc2 \
  --consumer-property group.protocol=consumer
```

> ★ **`group.protocol` 을 주지 않으면 예전 방식의 멈춤이 안 보일 수 있다.** 브로커는 이미 새 방식을 갖고 있고, **어느 쪽을 쓸지는 소비자가 고른다.**

**완료** — ④ 에서 나머지 둘이 영향받지 않고, ⑤ 에서 멈춘 데서 이어진다.

### 그룹이 어디까지 읽었는지 확인하기

```bash
docker compose exec broker /opt/kafka/bin/kafka-consumer-groups.sh \
  --bootstrap-server localhost:9092 --describe --group proc
```

`CURRENT-OFFSET` · `LOG-END-OFFSET` · `LAG` 이 나온다. **그룹마다 값이 다른 것**이 독립의 증거다.

### 생각할 것

> **브로커가 없었다면 이 셋을 어떻게 만들었을까.** 생산자가 세 곳을 알아야 했을 것이고, 네 번째가 붙는 날 생산자를 고쳐야 했을 것이다.

> **⑦ 에서 본 것** — 「멈춘다」는 사실이 **프로토콜 세대에 따라 범위가 다르다.** 문제가 사라진 것이 아니라 **전원이 멈추던 것이 옮겨가는 것만 멈추는 것으로** 줄었다.

## P4 · 빼기 회고 (10분)

**① 오늘 갖춘 구성을 종이에 적는다** — 브로커 · 토픽 · 파티션 · 소비자 셋

**② 하나를 골라 뺀다. 그리고 그때 잃는 것을 옆에 적는다**

```
뺀다 :  ______________________________
잃는다: ______________________________
```

**③ 답한다**

> **소비자가 하나뿐이었다면 브로커가 필요했을까.**

**④ 한 장으로 제출한다. 이름을 쓰지 않는다.**

**완료** — **「뺀다 ↔ 잃는 것」이 짝으로** 적혀 있다. 뺀다는 말만 있으면 미통과다.

★ **「브로커 자체를 뺀다」도 답이 된다** — 근거가 있으면. 3교시에서 본 네 시스템 중 범용 브로커를 운용하는 곳은 **0건**이었다.

★ **12회차 최종 발표의 「배제 근거서」가 이 형식이다.** 오늘이 연습이다.

---

## 오늘 정리 — 다음 주에 이어지는 것

- 오늘 만든 토픽 **앞에** 다음 주에 수집 계층이 붙는다
- 오늘 손으로 친 생산자 자리가 **브리지로 교체**된다
- **교체가 되는 것 자체가** 오늘 배운 결합도 분리의 증거다 — 브로커는 생산자가 무엇인지 모른다

> **오늘 정한 토픽 이름과 키 구조는 다음 주에 그대로 쓴다.** 설계서를 잃어버리지 않는다.

## 부록 — 오늘 쓴 명령 한눈에

| 무엇 | 명령 |
|---|---|
| 토픽 목록 | `kafka-topics.sh --bootstrap-server localhost:9092 --list` |
| 토픽 만들기 | `kafka-topics.sh … --create --topic T --partitions N --replication-factor 1` |
| 토픽 살펴보기 | `kafka-topics.sh … --describe --topic T` |
| 넣기 | `kafka-console-producer.sh … --topic T --property parse.key=true --property key.separator=:` |
| 읽기 | `kafka-console-consumer.sh … --topic T --group G --from-beginning` |
| 그룹 상태 | `kafka-consumer-groups.sh … --describe --group G` |

**앞에 붙는 것은 늘 같다** — `docker compose exec broker /opt/kafka/bin/`
