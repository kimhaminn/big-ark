# 용어 카드 — 5주차 엣지 수집 (MQTT)

> 한 장 요약. 실습 중에 되돌아본다.

---

## 한 줄로 남길 것

> **MQTT 는 기본적으로 버린다.**
> **구독자가 없는 순간의 메시지는 그대로 지나간다 — 그것을 전제로 가벼워진 프로토콜이다.**

---

## 이름부터 — 흔한 오해 하나

**`MQTT` 는 지금 약어가 아니다.** 처음 IBM 사양에서는 「MQ Telemetry Transport」였고, 그 `MQ` 는 **IBM 의 MQ Series 제품명**에서 왔다. 표준화 기구로 넘어간 뒤 **사양은 약어를 풀지 않는다.**

> 검색하면 「Message Queuing Telemetry Transport」도 나온다. **기술위원회 이름이 실제로 그렇다.** 둘 다 나오지만 **사양 쪽을 따른다.**
>
> ★ **풀어 쓰면 「큐」라는 인상이 생기고, 그것이 이 프로토콜에 대한 가장 흔한 오해다.**

---

## 용어 여덟

| 용어 | 한 줄 정의 | 왜 중요한가 |
|---|---|---|
| **토픽** | `/` 로 나뉜 문자열 | **만들지 않는다 — 발행하면 생긴다.** 그래서 오타가 새 토픽이 된다 |
| **와일드카드 `+` `#`** | 한 레벨 / 그 아래 전부 | ★ **구독자만 쓴다.** 발행자가 쓰면 그런 이름의 토픽이 생긴다 |
| **QoS 0 / 1 / 2** | 잊는다 / 재전송한다 / 정확히 한 번 | ★ **구간마다 따로 걸린다.** 끝에서 끝까지의 보증이 아니다 |
| **세션 (`clean_session`)** | 구독과 미전달분을 브로커가 붙잡는다 | **재전달 약속이지 보관이 아니다.** 되감을 수 없다 |
| **retain** | 토픽의 마지막 값 하나 | **상태값에 쓰고 이벤트에 쓰지 않는다.** 이력이 아니다 |
| **유언 (LWT)** | 끊길 때 브로커가 대신 발행 | 단말의 부재를 **단말이 아니라 브로커가** 알린다 |
| **브리지** | 구독해서 프로듀스하는 것 | **그 이상은 직접 만든다** — 키·재개·메타는 안 따라온다 |
| **공유 구독** | 같은 구독을 여럿이 나눠 받는다 | **5.0 에만 있다.** Kafka 컨슈머 그룹의 자리 |

---

## 지난주와 무엇이 다른가

| | Kafka (4주차) | MQTT (5주차) |
|---|---|---|
| **누가 붙는가** | 서버 · 서비스 (상시 연결) | **단말** (간헐 연결, 배터리·대역폭 제약) |
| **무엇을 보관하는가** | **로그를 남긴다.** 오프셋으로 되감는다 | **흘려보낸다** |
| **토픽의 모양** | 평면 + 파티션 | **계층 + 와일드카드** |
| **토픽을 만드는가** | `--create` 로 만든다 | **발행하면 생긴다** |
| **병렬 소비 단위** | 파티션 · 컨슈머 그룹 | **없다** (5.0 공유 구독이 그 자리) |

---

## 세대 — 무엇을 쓰는지 먼저 확인한다

| | 언제 | 무엇이 더 있는가 |
|---|---|---|
| **3.1.1** | 2014 표준 | — (현장 단말이 여기 묶여 있는 경우가 많다) |
| **5.0** | 2019 표준 | 이유 코드 · 만료 · 사용자 속성 · **공유 구독** |

> **브로커는 대개 둘 다 받는다. 못 고르는 쪽은 단말이다.**
> 단말은 펌웨어이고, 펌웨어를 바꾸려면 현장에 나가야 한다.

---

## 계보 — 왜 1999년 프로토콜이 2014년에야 표준인가

```
1999  개발 (IBM + Arcom) — 송유관 원격 감시, 위성 회선
2010  IBM 이 v3.1 을 무상 공개        ← 여기가 갈림길이다
2014  OASIS 3.1.1 표준
2019  OASIS 5.0 표준
```

> **11년간 사내 프로토콜이었다.** 좋아서 퍼진 것이 아니라 **풀어 놓은 뒤에** 퍼졌다.
> 3주차에 본 구글 논문과 같은 모양이다 — **놓아야 퍼진다.**

---

## 도입 전 체크리스트 — 셋에 답할 수 없으면 아직이다

| # | 질문 | 답할 수 있는가 |
|---|---|---|
| 1 | **단말이 많고 자주 끊기는가** | |
| 2 | **페이로드가 작고 잦은가** | |
| 3 | **양방향이 필요한가** | |

**둘 이상 걸리면 이 유형을 본다.** 그리고 **거의 언제나 버스 앞단**이므로 **경계의 번역기를 함께 설계한다.**

### 언제 두지 않는가

| 조건 | 대신 무엇이 는가 |
|---|---|
| 단말이 **서버뿐**이다 | 이미 상시 연결이다 — 계층 하나가 그냥 는다 |
| 페이로드가 **스트림**이다 | 프로토콜 수가 는다 (`Vamos` 는 넷을 다룬다) |
| 소비자가 **하나**이고 단말 주소를 안다 | 배포가 커진다 — 단말이 늘면 서버를 고쳐야 한다 |

## 오늘 본 실운영 사례 셋

| 프로젝트 | 토픽 설계 | 왜 그렇게 갈렸나 |
|---|---|---|
| **Fargus** (터널 화재감지 시스템) | `/Sensor` **하나** | 소비 계통이 NiFi **한 갈래**다. 가를 이유가 소비 쪽에서 안 생겼다 |
| **Firetrace** (소방관 위치측위 시스템) | 계층 **5개** (업링크 4 + 다운링크 1) | **관을 갈라야 품질을 따로 준다** — 열화상만 QoS 0 |
| **Vetura** (보훈재가복지 IoT 시스템) | 업무 단위 **5개** | safety 3종이 **한 벌로 움직인다** |
| **Vamos** (전광판 감시 시스템) | ★ **쓰지 않는다** | 단말이 카메라다 — 페이로드가 프레임이고 연결이 이미 스트림 |

> **같은 유형을 골랐는데 셋 다 다르게 갈랐다.** 유형이 정하는 것은 배관의 종류이고, **무엇이 어느 관으로 흐르는지는 소비 쪽이 정한다.**
>
> 그리고 넷째는 **이 유형을 쓰지 않았다.** 엣지 수집 계층은 있는데 **경량 메시징이 아닌 것으로** 채웠다.
